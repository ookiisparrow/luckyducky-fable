   部输入直接污染模型，但引入了新问题：

   • 持续的人工负载：对于一个“持续服务”的小程序，用户反馈、客服消息、评价、崩溃报警是持续流
     入的。若全部由一人筛选，无论频次是实时、每小时还是每天，都会形成长期负担，最终要么积压
     ，要么草草分类。
   • 筛选标准未定义：工单应包含哪些字段？优先级如何划分？何为“紧急”？没有标准，筛选结果会随
     筛选者状态波动。
   • 筛选者本身也是单点：这个人可能疲劳、误解、遗漏，且没有第二人复核。v2 用“人工”替代了“模
     型自动分类”的风险，却把风险转移到了人的可靠性上。
   • “仅收集”的技术含义模糊：如果收集端用 LLM 做摘要、OCR、关键词提取，原始信息已经在进入模
     型时被过滤或曲解；如果不是，那反馈入口只能收集原始文本/图片，无法做初步去重或聚合，人
     工筛选负担更重。
   • 紧急反馈缺乏直通机制：线上严重 bug 若走“收集 → 人工筛选 → 建单 → A 处理”，中间任何一步
     延迟都会扩大事故。

   结论：人工筛选是必要安全阀，但 v2 没有给出让它可持续运行的设计。

   ────────────────────────────────────────────────────────────────────────────────

   中等

   5. 任务路由的分类器本身没有验证，错分会直接导致模型错配

   理由：v2 把固定角色改为按任务类型路由，但“任务类型”由谁判定？方案没有说明。最可能的实现
   是由主控 A 在进场时判定，但这就产生了新的单点：

   • 一个涉及安全逻辑的日常小改，可能被 A 误判为“L2 日常”而只走 A 单干，错失 ChatGPT 的安全
     核查；
   • 一个普通的长 diff 重构，可能被 A 判定为“大范围审查”而触发 Kimi，造成不必要的成本；
   • 一个 bug 是否属于“疑难”，只有在 A 尝试后才知道，若一开始就路由到 kimi+chatgpt，会浪费
     token；若先让 A 尝试再升级，又浪费时间。

   没有独立校验的分类器，模型路由就是“让最短板的模型决定要不要请长板”。

   6. “项目记忆在文件系统不在会话”低估了会话上下文的价值

   理由：v2 用这条理由把常驻主控分配给上下文 128K 的 DeepSeek。但即使重要状态在文件系统，以
   下场景仍严重依赖会话上下文：

   • 检索哪些文件：一个复杂需求涉及 10+ 文件，A 需要记住最近探索过哪些、为什么排除某些方案
     、用户的隐性偏好。
   • 推理链条：RAG/文件系统只能提供片段，跨片段的推理链仍在会话中。
   • 工具调用历史：哪些测试跑过、哪些命令失败过、为什么改用 plan B。

   DeepSeek 128K 对常驻主控仍可能吃紧，尤其是长期项目。v2 没有给出当 A 的上下文接近上限时的
   主动归档/摘要/切换策略。

   7. L0 关键节点的判定比例未量化，成本与覆盖率难以平衡

   理由：v2 明确 L0 走 3× 成本的交叉验证，但没有定义：

   • 多少比例的任务会被判为 L0？
   • 由谁/按什么规则判定？
   • 如果 L0 比例过高，成本是否可承受？如果过低，安全事件是否会漏网？

   在单人维护、订阅三家 API 的场景下，“关键”是一个会被成本压力不断侵蚀的阈值。没有量化基线
   ，v2 无法落地为可执行的预算。

   8. “宁停勿猜”的阻塞策略与“几乎全自动”目标存在张力

   理由：v2 降级策略规定“安全类任务阻塞不降级（宁停勿猜）”，这是正确的安全原则。但在单人维
   护场景下：

   • 阻塞意味着流水线停下来等人；
   • 如果阻塞频繁发生（API 限流、模型输出异常、L0 缺一票、安全类任务触发），“全自动”就退化
     成“频繁等待人工的半自动”；
   • 当维护者不在线时，阻塞没有升级/通知机制。

   v2 没有说明阻塞时的通知、超时、升级策略。

   9. 降级接管主控时上下文重建成本未考虑

   理由：v2 说主控模型不可用时由 kimi 或 chatgpt 接管。但主控的会话状态（包括当前进行中的任
   务、最近的探索、未提交的决策）在另一个模型进程中不存在。虽然 v2 说项目记忆在文件系统，但
   ：

   • 另一个模型需要花时间重读、重推理；
   • 可能误解文件中的“决策日志”和未完成的中间状态；
   • 如果原主控正在处理一个插单，切换可能导致状态不一致。

   v2 没有给出主控切换前的状态快照/交接协议。

   ────────────────────────────────────────────────────────────────────────────────

   轻微

   10. 落地阶段验收标准与“只陈述意图”声明自相矛盾

   理由：v2 先说“只陈述意图与原则，不绑定任何具体实现”，后在“落地阶段”给出“三模型可路由”、“
   跑通一次 L0”、“工单进流水线”、“闭环运转”等具体验收标准。既然不绑定实现，验收标准就无法具
   体；既然要验收，就必须绑定某些最低实现要求。二者存在逻辑矛盾。

   11. “根因账本(ground truth)”与“可审计决策日志”的关系未澄清

   理由：v2 在架构图底部同时列出两者，但没有说明：

   • 什么级别的事件进 ground truth？
   • ground truth 由谁写入？
   • 决策日志引用 ground truth 的规则是什么？

   若 ground truth 也是 agent 写入，则与决策日志无本质区别；若只能由人工写入，则需说明人工
   职责。

   12. “定期盘点”未明确频率与责任人

   理由：v2 说“定期盘点（零模型成本脚本）列出待验证/已失效条目提醒人工”，但“定期”是每天、每
   周还是每月？“人工”是维护者本人还是有指定负责人？如果提醒被忽略，知识库污染会累积。

   13. 人工提审材料的准备与验证责任未明确

   理由：v2 流程最后一步是“提审材料（主控准备）→ 人工提审”。这里存在风险：

   • A 准备的材料可能遗漏隐私协议、类目资质、内容安全说明等；
   • 人工提审者（维护者自己）可能因信任 A 而疏于核对；
   • 若材料错误导致审核被拒，责任归属不清。

   ────────────────────────────────────────────────────────────────────────────────

   结论：需再修

   v2 相比 v1 有明显改进：采纳了人工筛选工单、降级策略、可审计决策日志、两轮制交叉验证、A
   不参与投票、按任务路由模型、分层权限白名单等关键意见。

   但 v2 仍然存在严重问题，不足以定稿：

   1. 核心安全机制（隔离/白名单/权限）从“流程约定”升级为“技术保障”的诉求没有真正满足，v2 反
      而用“意图层方案”回避了具体实现约束，使关键安全属性无法验收。
   2. 与项目既有 AGENTS.md 的硬约束衔接缺失，red/yellow/green 分级、部署人工授权、双轨锁等
      现实约束没有被纳入 v2 的 L0/L1/L2/L3 框架。
   3. 决策日志的信任模型仍是自我循环，没有外部 ground truth 或独立校验机制。
   4. 人工筛选工单环节被当作安全终点，但没有可持续运行的设计，在单人长期维护场景下会成为瓶
      颈。

   建议再修方向：

   • 把“隔离环境、互不可见、白名单权限”从意图声明改为最低实现约束（例如：B/C 必须运行在不同
     git worktree/不同 OS 用户/只读挂载；白名单必须列出具体工具清单及变更授权流程）。
   • 在方案中明确 v2 的 L0/L1/L2/L3 如何服从 AGENTS.md 的 red/yellow/green 分级，以及 red
     模块/部署/数据库不可逆操作的硬拦截点。
   • 给决策日志引入外部验证锚点：哪些结论必须由测试、lint、人工或实际线上结果验证后才能标记
     为“已验证”；明确 ground truth 账本的写入权限和与决策日志的层级关系。
   • 为人工筛选工单设计可持续机制：筛选标准/字段/优先级、批量处理节奏、紧急反馈直通 L0 的例
     外通道，以及当维护者不可达时的降级策略。

   定稿前至少需要再修一轮。
