## 2026-08-03 · 构建戳打瞎了部署漂移检测——上一批自己引入的回归（由代理评估考卷逮到·主力核实后修）

**病灶**：`deploy-fns.mjs` 的产物内容 hash 吃 `package.json` **全文**，而上一批（`00970a9`）新加的构建戳把提交号写进每函数 `package.json.version`（`0.0.0-<sha>`）→ **提交号一变，13 个函数 hash 全变**，「变更待部署 N 个」**恒等于全量**，再分不出谁真改了。而这条 hash 机制当初正是为治「假报 0 个」而建（`deploy-fns.mjs` 头注：app 函数落后 git 半月无人察觉）——**从漏报变成全是噪音，两种失效方式，都等于没有信号**。

**来源**：omp 代理能力评估 R03（诚实度专项）中由 `claude-opus-5` 在**零云端权限**条件下实测发现（改一个 sha → 13 个 hash 全变），主力独立核实属实（`deploy-fns.mjs:51` 的 hash 确含 `package.json`）。**考卷的副产品比考卷本身值钱**的一例。

**修**：`version` 排除在 hash 外，deps/name/其余字段照旧参与（`stripBuildStamp` 解析失败时 fail-safe 退回全文 hash——宁可多报一次，不能因解析失败静默放行内容变更）。**代价明写在代码注释里**：仅提交号变而产物内容不变时不再触发重部署，线上戳会停在「上次真有内容变更」那一版——内容仍对，只是戳不等于最新 HEAD；要让线上戳恒等 HEAD 需全量重部署换戳，值不值属部署面决策，未擅自替老板定。

**顺手收口**：hash 算法原有**两处镜像实现**（`deploy-fns.mjs` 内联 + `scripts/lib/deploy-drift.mjs` 的 `hashFnDist`），头注写「不能抽，因为 `openapi-perm-declared` 用正则原文锚定 deploy-fns.mjs 的 `'config.json'` 字面」——**实测该守卫只锚 `rewrite/cloud/build.mjs`，从不读 deploy-fns.mjs**，那条约束早已不存在（文档失真·与本轮考卷 R02 同族）。抽单源后「两处要记得同步改」的窄债一并消，`createHash` 死 import 同批清掉。

**验证**：守卫先红（新用例 1 failed/13 passed）→ 改到绿 → 反向自检（篡改一处必红 → **精确还原 + 字节级 `diff` 核对**）→ **真产物端到端**（跑一次构建后手改 dist 里的 version：hash 不变 ✓；加一个依赖：hash 照样变 ✓；还原后一致 ✓）。`npm run check` 全绿（114 条守卫 / 0 error / 143 文件 1579 测试）。

**主力自己踩的坑（记下来）**：反向自检第一次用 `git checkout --` 还原，**把尚未提交的修复整个撤销了**——同一轮考卷里 opus-5 的报告特意声明「精确还原、字节级核对，**未用 git checkout**」，避的正是这个。**改动未提交时，`git checkout` 不是还原篡改、是还原一切。**

## 2026-08-02 · omp 战役工单 W1：契约哨兵收官（15 action 全覆盖·A/B/C 三批·长批压测 × 编排实测）

**起因**：B10「按热度逐批扩」的收尾。app 网关 15 个低危 action 的响应形状仍是静默漂移面——mp 物理进不了 `@ldrw/shared`、响应形状全靠手抄，cloud 改键 mp 编译不红（病根#5 + #8）。工单要求分 3 批、一批一 squash、每 action 一个子代理查证单元。

**核心结论：网关的 15 个 action 分三类裁剪形态，哨兵写法必须跟着分**——这是本役最该留下的判断，不是"补了 17 个用例"。
> ① **零裁剪透传**（catalog/content/users/progress 面·`{...doc}` 或 `res.data` 整档下发）：响应键集由**写侧**单向决定，读侧零约束。写侧加一个字段就直接出公开网关，编译不红、既有值断言也不红。哨兵必须「经真写侧写入 → 网关读回」，锁「写侧字段集 ↔ 下发面」端到端契约；测试自造 seed 只锁得住自己的回声。
> ② **白名单重建**（getPublicFaq/getHelpVideos·逐字段 `String()` 重造）：库内脏字段物理进不来。哨兵该做的不是枚举现有内部列，而是**往 seed 里下毒**（塞白名单外字段）证明它们透不过来。
> ③ **零载荷写**（trackEvent/submitReview/submitFeedback·恒 `ok()`）：下发面为空集，写侧字段全在库里。哨兵锁「写入字段集 ↔ 零下发」这个对照。
> 另一条贯穿全批：**带闸 action 的失败态与成功态不同形**（成功的 list/items/user 键在失败时整个消失，mp 裸解构即 undefined），故失败态逐条单独锁。

**编排（工单②·workflow-fanout 模式A 适配实测）**：三批各派 5 个只读 scout 并行查证（读 handler 真实现 → 定键集 → 草拟哨兵 → 结构化 7 项返回），主会话**逐条亲核后统一落笔**——agent 一个字都没往仓里写。**等价性差异**（工单要求交卷时报告）：本代理无 Workflow `pipeline()` 脚本层，用原生子代理批量派发替代，故 ① 无 plan 文件与 `(prompt,opts)` 回放缓存，改规格＝直接重派，不存在"改了 spec 不许 resume"那条坑；② 无脚本层「改动文件 ⊆ 白名单」断言，改以 scout **只读**（物理无写权）替代，边界由能力而非断言保证；③ 无 `skipSpecLint`，规格预审由主会话亲读现场承担。模式A 的内核——**并行产出、串行亲核**——完整成立。
