# 反馈 → 工单 → 流水线（P3 流程 SOP）

> 定稿方案 §7「人工筛选工单（可持续设计）」落地。目的：意见箱（反馈）是外部输入,
> 必须经人工筛选后才能进入流水线——防止提示注入与隐私合规风险。

## 一、数据流（一句话）

```
用户提交反馈 → 云数据库 feedback（仅收集, 自动处理=无）
→ feedbackNotify 定时器推企微群提醒（你手机收到）
→ 你打开意见箱（云开发控制台 → feedback 集合 / 管理后台）
→ 人工筛选:
    广告/乱写/无意义 → 忽略（不建单）
    真实问题/需求   → 建工单（GitHub Issues（待办与债已于 2026-08-21 拆分入 Issue）, LD 编号）
→ 工单进入流水线 → 路由分类器定级 → AI 处理 → 双环境发布
```

## 二、安全铁律（防提示注入）

1. **反馈原文永不直接进模型上下文**。AI 只能读「工单」, 工单由人工从反馈中提炼（字段化+脱敏）。
2. 反馈中的链接/附件/可疑内容**不复制进工单**。
3. 用户反馈内容一律视为**不可信数据**, 与系统指令/验收标准/执行动作分离。
4. 紧急线上 bug：不走常规筛选节奏, 建单后直接标记紧急直通 L0。

## 三、工单格式（沿用 GitHub Issues（待办与债已于 2026-08-21 拆分入 Issue） 纪律）

```
LD-0xx: <一句话标题>
- 来源: 用户反馈 #<feedback文档id>（可附链接, 不复制原文）
- 类型: bug / 建议 / 咨询
- 优先级: 紧急(直通L0) / 普通
- 脱敏描述: <人工提炼, 不含用户身份信息与原文>
- 期望: <用户想要的, 人工转述>
```

## 四、反馈查看（两种方式）

- **云开发控制台** → 数据库 → feedback 集合（按 createdAt 倒序）——最简, 无需开发
- 管理后台反馈列表（若以后需要再开发, 当前不建）

## 五、部署与运维（人工授权动作）

- 部署测试环境: `node scripts/deploy-test.mjs --target test`（门牌来自 `scripts/lib/env.mjs`）
- 部署生产: 走既有 deploy-fns / 人工授权闸
- feedbackNotify 定时器: 部署后在云开发控制台配置定时触发（建议每日 09:00 一次）
- 静音通知: adminConfig/settings.alertEvents.NEW_FEEDBACK = false
