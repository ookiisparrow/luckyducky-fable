# 元模式——治理流水线

> 本项目治理只为两件事：
> 1. 挡住真实业务风险：钱、权限、状态、部署。
> 2. 挡住 AI 的幻觉：没验过却说通过、写过时或编造的名字、把否掉的方案再做一遍。
>
> 旧版框架（痛→守卫循环、覆盖率闸、五层验证网）在 git 历史里，用 `git log -- docs/元模式.md` 查。

## 为什么是这四步

2026-09-25 做过一次测量：
- **结构守卫拦下的主要是记账摩擦**：比如"加了守卫忘了改文档里的数字"，而不是真错误。
- **真正的幻觉类问题靠独立审查发现**：失败装成功、文档写死名字、死代码，这些都是审查代理找出来的。
- **最有效的是硬闸**：权限闸、编译器、CI，劝 AI 的文字规则效果最差。

所以流水线把力气放在"不让 AI 自己说了算"上，不放在多写规则上。

## 流水线

**1. 事实只从代码取**
- 名字、数字、清单、接口一律以代码为真值。文档只写"为什么"和"决定了什么"。
- 引用事实时写"以 `X` 为准"，不抄值，因为抄了必漂移（病根#11）。
- 注释里不写"由守卫 X 保证"这类承诺，除非这条守卫真在。写之前先 grep `scripts/check-structure.mjs` 确认。

**2. 危险区用权限拦，不靠文字劝**

| 闸 | 拦什么 | 谁开锁 |
|---|---|---|
| pre-commit 钱链闸 | 钱链路径的提交（清单以 `scripts/lib/moneychain-paths.mjs` 为准） | 老板授权 `MONEYCHAIN_ALLOWED=1` |
| commit-msg 红区复核 | 红区模块改动（清单以 `modules.json` 为准） | 提交信息带 `[red-review: 复核人]` |
| 部署闸 `guard-deploy` | 云函数、托管部署 | 老板授权 `DEPLOY_ALLOWED=1` |
| MCP 写工具封锁 | AI 直接调云端写工具 | 不可解锁 |

**3. "完成"只由机器判**
- 质量闸是 `npm run check`，pre-commit 和 CI 跑的是同一个。CI 另加 `npm run check:artifacts`（构建产物验证）。
- AI 说"过了"不算，要看 CI 结果。
- 新行为先写一个会红的测试，再写实现。测试必须能在逻辑被改坏时变红：改坏一处，看它红了，再还原。

**4. 声明带证据，人合并**
- PR 描述里凡是写"真机验过"、"压测过"、"对账过"，必须附日志、截图或命令输出。不附就当没做（病根#8）。这一条现在靠人核，没有机器闸。
- 人只做三件事：合并 PR、红区授权、部署授权。

## 守卫准入

加一条守卫之前，先过这张表：

| 值得机器守 | 不守（交给行为测试或 review） |
|---|---|
| 钱、权限、状态流转、部署 | UI 实现细节，比如哪个节点绑了哪个事件 |
| 手抄副本必须一致，比如小程序进不了 shared 包、只能落副本的常量 | 治理文档自身：计数、指针、覆盖率 |
| 没有编译器兜底的格式，比如 wxml、wxs、包体积 | 已否决的产品方案，除非它真的回潮过 |

几条补充规矩：
- **说得出来由**：新守卫要能说出防的是哪次真实事故或哪条红线，在 `roots` 字段标病根号。
- **同类合并**：同类窄守卫攒多了，合成"一张注册表 + 一条守卫"，新增时只加表行。
- **定期删**：复查时优先删两种守卫，一种是只在反向自检里红过、从没在真实改动里拦过东西的，另一种是守着已经删掉的功能的。

## 周期审查

- 独立审查代理批量找问题、出修复 PR，人来合并。它的价值在于换一双眼睛，不是写代码的那个 AI 自己检查自己。
- 积压会让审查失效。开着的 PR 多到看不过来时，先把现有的合并或关掉，再开下一轮审查。
