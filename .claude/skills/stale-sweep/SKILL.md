# stale-sweep · 过时信息清淤

> **定位**：本 skill 清的是「信息层的债」——会让任何进场者（人或 AI）产生误会、误解、歧义的残留物。
> 与既有工具分工：守卫管机器能钉死的（dead-exports/orphan-assets）；`/doc-audit` 管活文档瘦身；
> **本 skill 管跨层交叉核实**——「文档说的」与「仓库真实」之间的裂缝。

## 一句话纪律

**每一刀都要有证据（file:line），每一删都要先全仓 grep，每一批收工必须 `npm run check` 全绿。历史归 git，不写墓志铭。**

## 扫描范围（五类）

### A 类·死指针（指向不存在的东西）
- 文档/注释里的 docs 或 archive 目录下的文件引用（守卫已扫 .md 引用，本步扩到**无后缀路径**：`scripts/X`、`rewrite/cloud/src/X.ts` 等）
- 提到的 **npm script / 命令**不存在（如"跑 `npm run xxx`"但 package.json 无此 script）
- 提到的 **云函数/集合/环境标识**在 modules.json/cloudbaserc.json 中查无此人

### B 类·孤儿（存在但无人引用）
- scripts/ 下没有任何 README/package.json/docs 引用的脚本（先确认非"手动运维件"，运维手册提到的算被引用）
- docs/ 下不在 CLAUDE 路由表、不被其他文档引用、且内容已被取代的文件
- 判据：`grep -r "文件名"` 全仓（含 CLAUDE/skills/README）零命中 → 候选；删除前再人工过目一眼

### C 类·双源漂移（同一事实两个说法）
- 同一件事（备份方式/部署步骤/环境标识/凭证位置）在 ≥2 个文档各有描述且不一致
- 处理：留「单源」（通常是正册：工作流.md/运维手册/modules.json），其余改为一行指针
- 特别盯：本次刚重构过的面（备份链/拓扑/版本号）在其他文档里的旧影子

### D 类·过期断言（说的和做的对不上）
- 「TODO/待办/下一步/将要」→ 实际已完成（对照 git log 与 Issues）
- 「已存在/已配置/已上线」→ 实际查无此事（grep 代码/云端清单核实）
- 「剩 N 天」「当前 X 个」类**时效性数字**——一律改为「以某命令为准」，不留会腐烂的具体数

### E 类·误导性残留（最容易坑人的）
- 注释/头注指向已退役的账本、旧方案、旧路径（如「见 XX 日志第 N 条」）
- 被"刻意保留"声明包裹但其实已失效的 flag（保留声明本身也要复核是否仍成立）

## 执行流程

1. **机检先行**（零判断部分交给机器）：
   ```bash
   node scripts/check-structure.mjs          # 守卫基线（dead-exports/orphan-assets 已覆盖的面不重复报）
   npm run patrol                            # 顺带验证巡逻自身没坏
   ```
   再按上方 A–E 类逐类 grep（模式见各类小节）。
2. **逐条取证**：每条发现记 `类别 | file:line | 现状引文 | 核实方式 | 建议（删/改指/留证）`。
3. **分级处置**：
   - 🟢 直接清：死指针改直/删除、时效数字改指针、孤儿 md 删正文——**删前必须全仓 grep 引用为零**
   - 🟡 改指针：被取代的描述改为一行指向正册（`docs/工作流.md`/`docs/运维手册.md`/modules.json）
   - 🔴 报老板不动：涉及 red 模块语义、守卫增删、console-assets 正册、需求取舍——只开 Issue 记录
4. **反向自检**：清完后① `npm run check` 全绿；② 抽 3 条已删项反查「确实无人再引用」；③ 若误删，git 还原即可（历史即归档层）。
5. **交卷格式**：一张表——发现 N 条 / 清了 M 条 / 改指 K 条 / 报拍板 J 条（Issue 号），外加「本次未动清单及理由」。

## 红线

- 不碰 `scripts/check-*.mjs` 与 `.claude/` 下其他 skill 的语义（本 skill 自身除外）；清出的问题若需改守卫＝治理批，另行走审批
- 不删「业务预留」：先 grep 判例索引与需求清单，对得上号的预留不是垃圾
- 不为凑数清淤：宁少勿错，每一条都经得起「删了它谁会受影响」的反问
